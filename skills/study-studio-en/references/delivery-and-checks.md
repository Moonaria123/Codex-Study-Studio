# Delivery and meaningful verification

The designated book is the only knowledge baseline for content verification; official material verifies the syllabus and assessment format only. Check every important explanation, case rule, formula, term and knowledge relationship against a source locator and remove unsupported extensions. Ensure learning materials contain no protective disclaimers. Keep production gaps in verification records and delivery communication, outside the teaching content.

## Local and cloud delivery

Verify the reading root and chapter parent folders first. Stage new outputs and verify them before publishing. Preserve a recoverable previous version before replacing an existing target; do not perform unrelated cleanup. Prefer available cloud connectors when sufficient. If they cannot perform the required action, use a compliant local-sync or UI route and explain the difference.

After uploading, read back filename, size, MIME type and parent. When moving an old edition, remove only its verified old parent and retain any other parents. Compare the final target set with the initial inventory; leave unrelated outputs unchanged. Retain a delivery inventory with path/ID, version, size or checksum, verification and original location. Preserve the hub's stable file ID and practical local path. Mention backup export before updating and never clear browser data automatically.

A production request alone does not authorise public sharing or an external deployment. Follow the current authorisation for online voice/video costs, credentials and content transmission. Do not ask again about already authorised work or extend authorisation from an old course without a basis.

## Verification evidence

| Object | Minimum meaningful check |
|---|---|
| Chapter splits | Page count; visual first/last-page confirmation; every original-page mapping; unchanged original |
| Outline/Syllabus | Complete chapter index; book-only knowledge in Outline; verified official requirements only in Syllabus; unread/unverified scope recorded separately |
| CharpterReview | Subsection coverage; definitions, formulas, values, distinctions and relationships checked against the book; no external additions or overinterpretation; core-knowledge-to-module mapping |
| Slides/script | Actual renders of first/last, dense, formula and example slides; slide-by-slide script alignment; correct terminology and citations |
| Video | Measured part/total durations; complete audio and pictures; listening at start/middle/end; aligned captions without overflow; effective thinking pauses |
| Overview/PDF | Inspect exports; readable text when zoomed; no overlap, cropping or spelling errors; page breaks preserve meaning |
| Interactive hub | Actual browser clicks through tools, chapters and answers; reload recovery; separate save, discard and cancel-exit checks; restored map view; image exports |
| History/mistakes | Frozen original questions and answers; correct marks and elapsed time; repeated saves of one attempt do not inflate mistakes; a second independent attempt can add mistakes; complete printable PDF |
| Backups | Populate actual progress/history/map state, export and import into fresh browser storage, then compare; invalid, cross-course and malicious files execute no code and leave current data unchanged |
| Chapter extensions | New chapter works; old IDs and records remain recoverable; revised answer keys do not rewrite history |

Pause learning-time accounting outside learning screens or when the page is hidden. Define exam timing separately; do not present study timing as an official rule. Use shortened or expired timers to verify races between automatic submission and exit dialogues. Test feedback visibility separately for practice and exam modes.

For the first complex hub or a data-recovery change, an independent reviewer should inspect input validation and history protection, followed by actual browser verification. Review does not replace execution. Broaden checks only for new changes or failures; do not repeatedly run unrelated suites. Use synthetic content and isolated browsers, without clearing real user records.

## Version recovery

A complete JSON backup includes course identity and schema version, map state, unfinished progress, history snapshots, the mistake data derived from them, card edits and settings. Validate structure, size and course compatibility before import; make replacement/merge behaviour clear and leave current data unchanged on failure. Knowledge content is embedded in the HTML; a learning-record backup does not replace the textbook.

Uploading to cloud storage does not synchronise browser-local records across devices. Changes to file paths, browser profiles or storage policy can create a new storage area. Import must restore a previously exported backup of the same course. Label a separate HTML history report as an additional readable/shareable snapshot, not a complete recovery file.

Do not assume that old chapter pages with existing learning records can be read or migrated automatically. Inspect their actual formats and export capabilities. Provide an explicit conversion when supported; otherwise retain the old files and explain the limitation. Archiving is not deletion.
